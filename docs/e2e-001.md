# E2E-001 — fragments-based systemPrompt composition

## Goal

End-to-end verification of spec 001 outside the bun unit-test harness,
on the actual installed `@nexquark/pi-subagent-fragments` package
(version 0.1.0) running against the real `@earendil-works/pi-coding-agent`
peer.

This is the integration test that the unit suite cannot substitute for:
bun's `tests/preload.ts` mocks `@earendil-works/pi-coding-agent` with a
simplified line-based parser (see `tests/prompt-compose.test.ts` header
note), so the unit suite proves the helper logic but cannot prove that
the real YAML parser, the real agent-load loop, and the real spawn-time
artifact writer agree on the final prompt content.

## Setup

The fork was installed globally from a packed tarball:

```sh
npm pack                                   # → nexquark-pi-subagent-fragments-0.1.0.tgz
npm install -g ./nexquark-pi-subagent-fragments-0.1.0.tgz
node $(npm root -g)/@nexquark/pi-subagent-fragments/scripts/append-system.mjs install
```

`pi list` does not surface global npm packages unless they are also
listed in `~/.pi/agent/settings.json`, so the E2E driver invokes the
fork directly via `import` rather than through a `pi` session. The
`@earendil-works/pi-*` peers are resolved through a `NODE_PATH`
symlink farm under `e2e/local_node_modules/`.

## Fixtures

```
e2e/fixtures/test-frag-role.md     (fragment 1, 90 bytes)
e2e/fixtures/test-frag-style.md    (fragment 2, 77 bytes)
e2e/fixtures/test-frag-agent.md    (agent frontmatter + body)
```

Agent frontmatter:

```yaml
---
name: e2e-frag-test
description: e2e fragments test agent
systemPromptFragments: ["./test-frag-role.md", "./test-frag-style.md"]
systemPromptMode: append
pane: false
---

AGENT-BODY-START
You are a test agent. Respond with FRAGMENT-A-START / FRAGMENT-B-START marker strings verbatim.
AGENT-BODY-END
```

Each fragment file contains a unique `FRAGMENT-X-START` / `FRAGMENT-X-END`
pair so a downstream checker can verify both presence and ordering
without parsing the prompt structure.

## Driver

`e2e/e2e-001.mjs` (run with `NODE_PATH=./e2e/local_node_modules bun run
e2e/e2e-001.mjs`):

1. Builds `FAKE_PROJECT/.pi/agents/` under a fresh tmp dir and copies
   the three fixture files into it. Using a tmp project layout avoids
   contaminating the real `~/.pi/agent/agents/` or any real project
   under `/home/openatom/codes/`.
2. Calls `discoverAgents(FAKE_PROJECT, "project")` and locates the
   `e2e-frag-test` agent.
3. Asserts `systemPromptFragments` and `systemPromptMode` are populated
   from the frontmatter (kebab/camelCase aliases, inline-array shape).
4. Calls `writeLauncher(RUNTIME_ROOT, parentSessionId, cwd, agent, ...)`
   — the same function `pane.ts` uses during a real persistent-pane
   spawn — and reads the resulting `promptFile` back from disk.
5. Asserts that the prompt file content:
   - Contains all six marker strings (3 × START, 3 × END).
   - Contains the default separator `\n\n---\n\n`.
   - Presents the markers in declared order
     (fragment-A → fragment-B → body).
   - Has no separator after the body (body is the last segment).

## What this proves against spec § 4.5 case 3

- The real (non-mocked) YAML parser from
  `@earendil-works/pi-coding-agent` correctly resolves inline-array
  fragment paths against the agent file's directory.
- `loadAgentsFromDir` reads each fragment synchronously and folds its
  contents into `agent.systemPrompt` in declared order.
- `writeLauncher`'s spawn-time composition (`composeAgentPrompt({
  body: agent.systemPrompt, fragments: [], mode: agent.systemPromptMode
  })`) is a no-op for v1 (the body already contains the joined
  fragments, so passing `fragments: []` produces the same content) but
  the import + call shape is now in place so v2 can substitute dynamic
  loading without touching the two spawn call sites.
- The default separator `\n\n---\n\n` separates fragments and body.
- The body is the final segment of the composed prompt.

## Limitations (explicitly out of scope)

- This driver does not actually launch `pi` as a subprocess, does not
  allocate a tmux pane, and does not invoke an LLM. The fork's spawn
  pipeline ends at writing the prompt file plus the launcher script
  shell snippet; downstream of that is the unmodified upstream
  `pi-agents-tmux` behavior.
- The `e2e/local_node_modules/` directory contains symlinks to
  `@earendil-works/pi-*` peer packages installed by pi itself. It is
  not part of the published package and not part of the published
  source tree's `files` whitelist (see `package.json`); it is git-ignored.
