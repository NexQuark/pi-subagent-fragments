## 2. OQ 2 — History persistence location

**Question**: `~/.cache/pi-subagent-fragments/prompt-history/<agent>.json`
(survives session restart) vs `runtimeRoot/prompt-history/<agent>.json`
(session-scoped).

**Ruling**: **session runtime dir** — `runtimeDirForContext(ctx)` +
`prompt-history/<agent>.json`.

Rationale:
- History entries capture `prev`/`new` system prompts tied to a live pane
  agent's conversation; the agent's session file itself is already
  session-scoped (`~/.pi/agent/vstack/sessions/<sessionId>/pi-subagent-fragments/sessions/`).
  Keeping history beside the pane registry (`panes.json`), task registry
  (`tasks.json`) and session files keeps one lifecycle, one cleanup story.
- `~/.cache` would leak across machines/sessions and survive the agent being
  stopped+removed — stale rollback targets for a dead agent.
- Session-scoped means `--rollback` after a session restart on the **same**
  live pane is still valid (the pane session file persists across restarts of
  the *parent*; runtime dir is keyed by parent session id via
  `runtimeSessionId(ctx)`), which matches how pane registry already works.

**Amendment**: spec § 3.4 storage line changes to the session runtime dir path;
§ 7 OQ2 marked RESOLVED with this ruling.

## 3. OQ 3 — `--append` semantic (`<pi-default>` opacity)

**Question**: pi's default system prompt is opaque to the extension; what does
`--append` mean?

**Ruling**: `--append` = **"append to whatever the agent's effective prompt
currently is"**, i.e. the hook reads `event.systemPrompt` (the fully assembled
effective prompt for the upcoming turn — includes pi-default + any prior
`--append-system-prompt` content) and appends `<new>` to it.

This redefines the three modes uniformly at the hook:

```
--replace → effective = <new>
--append  → effective = event.systemPrompt + <new>
--add     → effective = event.systemPrompt + <new>   (identical to --append!)
```

Wait — that collapses `--append` and `--add`. Let me restate the distinction
at the **write side**, where `current` is known:

- `--replace`: state.systemPrompt = `<new>` (drop everything).
- `--append`: state.systemPrompt = `<computed-at-write-time current effective>` + `<new>`.
  The write side does **not** know pi-default; it uses the agent's current
  system prompt as recorded in the pane registry / synthesizer, which already
  includes the pi-default base when the agent was launched via
  `--append-system-prompt`. Result: pi-default preserved + new appended.
- `--add`: same composition as `--append` **today** (both = current + new).

The `--append` vs `--add` distinction only materializes when a subsequent
mutation follows: because the state file stores the **fully composed**
effective prompt, the next `--append` starts from that composed value (new
base), whereas `--add` is its alias. **Recommendation**: keep both flags
parsed (R2 grammar lock), implement `--add` as explicit alias of `--append`
in v1, and document that they are aliases until a later version introduces a
per-segment base concept. This is a **spec amendment** (§ 3.2 table:
`--append` row's `<pi-default>` column becomes "preserved as part of current
effective prompt"; note that `--append` and `--add` are aliases in v1).

**Alternative rejected**: trying to read pi-default via
`ExtensionContextActions.getSystemPrompt()` and reconstruct — unreliable
(returns only what the extension knows, and pi-default lives outside that).

## 4. OQ 4 — `/agents:inject` on ad-hoc / non-live agents

**Question**: ad-hoc agents (spec 002 synthesized) have no persistent session;
should inject fail?

**Ruling**: **fail with a clear error** for targets without a live persistent
pane session:

```
Error: inject: <name> has no live pane session to inject into
```

- `findAgent(name)` (persistent pane registry) — hit → proceed.
- Otherwise try `synthesizeAdhocAgent` — if the synthesized config exists but
  no live pane → same error (bg one-shots already exited).
- Unknown name → `Error: Unknown agent: <name>` (existing behavior).

Acceptance criterion "Mutating an unknown / dead agent → error" already covers
this; amend the wording to "unknown, dead, or non-pane agent".

## 5. OQ 5 — `--cwd` semantics in inject

**Question**: does inject's `--cwd` change the agent's runtime cwd (pi doesn't
support mid-session chdir) or only fragment-resolution root?

**Ruling**: **resolution root only** (plus the target pane must already live
in a cwd; we do NOT attempt to chdir the running agent).

- `parseInjectArgs` accepts `--cwd <path>`; used only for `#<file>` /
  `#"..."` / `@` source resolution via `tryResolveAsFile` (same helper as spec
  002 — single source of truth).
- The state file stores the resolved effective prompt; the hook never sees
  cwd.
- Document: "`--cwd` in inject sets the source-resolution root only; it does
  not relocate the running agent."
